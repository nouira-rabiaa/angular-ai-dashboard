## Infrastructure et chargement

Une seule bibliothèque : Transloco **8.4.0**, épinglée en UX-3A. Ses contraintes `@angular/core >=16.0.0` et `rxjs >=6.0.0` sont compatibles avec Angular 19. `reRenderOnLangChange` permet le changement à chaud sans reconstruction ni rechargement. Référence : [configuration officielle](https://jsverse.gitbook.io/transloco/getting-started/config-options).

Les catalogues `client/src/app/i18n/catalogs/fr.json` et `en.json` contiennent **788 clés chacun** : libellés visibles, noms accessibles, descriptions, confirmations, états et erreurs frontend. Les descriptions de la démo et du diagramme utilisent des clés ; identifiants, routes, endpoints et connexions restent inchangés. Les noms des technologies restent littéraux ; les qualificatifs explicatifs sont traduits.

Les deux catalogues complets sont importés dynamiquement. L’initialiseur Angular attend le français de fallback, puis la langue choisie, avant le premier rendu. Le français complet est donc également chargé pour un utilisateur EN. Un petit `shell-fr.json` de 36 clés conserve la navigation et un message d’échec compréhensible si le chargement français échoue. Aucun service externe de traduction ou appel IA n’est utilisé.

Une clé anglaise manquante utilise le français. Une clé inconnue des deux catalogues affiche un libellé de secours et produit un avertissement en développement, jamais la clé brute. Transloco gère l’interpolation ; les compteurs emploient notamment des libellés nominaux (« Composants : … ») pour éviter des accords incorrects sans ajouter un plugin de pluralisation.

## Langue, persistance et états

`UiLanguageService` centralise `fr` / `en`, les Signals et l’accès défensif à `localStorage`, sous la clé `enterprise-ai-dashboard.ui-language`. Le défaut est français, indépendamment de la langue du navigateur. Un accès au stockage refusé ne bloque pas la sélection en mémoire. Une préférence inconnue est ignorée. Un échec de chargement anglais conserve le français ; les chargements hors ordre ne peuvent pas remplacer le dernier choix.

Le sélecteur du header comporte des boutons natifs nommés, un état `aria-pressed`, un focus visible et un indicateur de chargement. `document.lang`, les titres du navigateur et les noms accessibles suivent la langue. Le RouterOutlet, les formulaires et les composants actifs restent montés.

## Séparation des textes et données métier

La langue UI est indépendante de la langue configurée d’un agent. La bascule ne modifie jamais les noms, descriptions, instructions système, messages de secours enregistrés, documents, extraits, conversations, réponses du fournisseur ou schémas générés. Ces contenus peuvent donc rester français dans une interface anglaise, ou l’inverse.

Les confirmations et erreurs créées par le Générateur portent des métadonnées UI distinctes (`uiKey`, `uiParams`), résolues à l’affichage. Les réponses réelles restent dans `text`. Les titres, champs, options et placeholders fournis par un schéma IA restent des données métier ; seuls les contrôles génériques et messages de validation du formulaire sont traduits.

Les états frontend de notification conservent leurs clés jusqu’au rendu afin qu’un message déjà affiché change aussi de langue. Les statuts connus sont localisés pour l’affichage ; leurs codes et propriétés JSON restent inchangés. Les codes techniques inconnus restent identifiables. Les erreurs sont choisies selon le statut HTTP ou le contexte frontend, sans comparaison fragile du texte libre du serveur. Le corps libre d’une erreur serveur n’est pas traité comme une traduction ni présenté comme une réponse IA.

Aucune sauvegarde, requête RAG, nouvelle inférence, modification de budget ou réinitialisation de formulaire n’est déclenchée par la bascule. Les protections des brouillons et les conversations persistantes du Studio sont conservées. Aucun changement backend, SQLite, Groq, API, calcul FinOps, permission ou authentification. Le produit reste local et sans authentification.

## Formatage

`UiLanguageService` utilise Intl avec `fr-FR` / `en-US` pour les nombres, pourcentages, dates et devises. Les valeurs indisponibles restent explicites. Les récapitulatifs monétaires gardent deux décimales et les détails gardent leur précision existante. La devise réelle reste **USD** : le français peut afficher `$US`, l’anglais `$`, sans conversion en euros ni modification numérique.

Les dates calendaires FinOps et étiquettes quotidiennes gardent UTC. Les horodatages auparavant rendus par Angular DatePipe conservent le fuseau local via `UiDatePipe`. Le `LOCALE_ID` existant n’est pas modifié ; les affichages concernés utilisent désormais la locale UI explicitement. Les valeurs ISO des filtres et champs date ne changent pas. Les contrôles date et nombre natifs peuvent suivre les conventions du navigateur/système.

## Contrôles automatisés

Depuis `client` :

```sh
npm ci --legacy-peer-deps
npm run check:i18n
npm test -- --runInBand
npm run build
```

Depuis `server` : `npm test` utilise les mocks et bases isolées existants, sans appel IA réel. `git diff --check` contrôle les espaces du diff.

`check:i18n`, exécuté avant le build, vérifie les clés FR/EN, valeurs non vides, paramètres d’interpolation et références statiques dans les templates et fichiers TypeScript. Il parse également les templates Angular pour détecter les textes statiques et attributs de présentation non localisés. Cela ne constitue pas une preuve automatique de qualité linguistique ou visuelle dans tous les états.

Les tests couvrent la navigation sur les cinq routes, les six étapes et quatre parcours, les états FinOps (80 %, 100 %, neutre et indisponible), les erreurs et validations, le formatage, la persistance et le fallback. Ils vérifient aussi la conservation des brouillons, contrôles, sélections documentaires, conversation active, citations et valeurs métier, sans nouvelle requête lors d’une bascule.

Validation finale UX-3B : **21 suites / 166 tests Angular réussis**, **115 tests backend réussis**, contrôle des 788 clés et `git diff --check` réussis. Build production réussi sans avertissement Angular. Les tests existants sont conservés et adaptés aux libellés/formatages localisés ; 14 nouveaux tests vérifient la couverture bilingue et les états préservés.

## Mesures du build UX-3B

Le build production mesuré contient **439 628 octets initiaux**, contre **454 660** en UX-3A. Les catalogues différés pèsent **62 030 octets (FR)** et **53 546 octets (EN)**. Le total initial Angular exclut ces imports dynamiques, mais le catalogue français est requis au démarrage, et l’anglais est requis si EN est sélectionné. **La baisse du total initial n’est donc pas une baisse équivalente du téléchargement nécessaire au premier affichage.** Ces mesures sont des tailles brutes ; les estimations de transfert du build sont distinctes.

Les cinq routes restent lazy ; les budgets sont inchangés : initial 500 kB / 1 MB, composant 4 kB / 8 kB. Le stylesheet de composant maximal reste à **3 971 octets**. Aucun fichier SCSS n’est modifié pour UX-3B.
